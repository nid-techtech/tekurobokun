# テクロボくん 本来構想仕様書（イベント交流用ロボット・統合版）
 
## 0. 本書の位置付け
 
本書は、ものづくりサークル「TECH✩TECH」のマスコットキャラクター「テクロボくん」を模したロボットについて、**ヘボコン出場を機に着手した本来の構想（文化祭等のイベントで参加者と交流できるロボット）の全体像**を仕様化するものである。
 
先行して作成した `tekurobo_hebocon_spec.md`（以下「Phase 1スペック」）は、大会出場に必要な最小限の機能に絞った暫定版であり、その1.2節では以下を「今回実装しない機能（将来拡張・スコープ外）」として明示的に見送っていた。
 
- Google STT / Gemini API による音声対話
- リアルタイムTTS
- Webカメラ入力
- 「30cm前進して」のような音声コマンドによる距離・角度指定制御
- 発話内容に応じた高度な感情表現ロジック
本書はこれらの見送った機能を含め、**本来の構想全体（Phase 2）**を仕様化し、あわせてPhase 1で採用したアーキテクチャがPhase 2への拡張にどこまで耐えるかを検証する。
 
**本書は実装指示書ではなく、設計検討・要件整理を目的とした文書である。** Phase 2の着手時期・実装順序は未定であり、Claude Codeへの実装依頼はPhase 1スペックの範囲にとどめる。

## 2. Phase 2で目指す動作目標（原構想の再整理）
 
- 無操作時の振る舞い（フェイシャルの動き、履帯による自走）による有機的・生物的な雰囲気の演出（Phase 1より精緻化）
- Google STT・Gemini API・TTSエンジンにより、「テクロボくん」のペルソナを与えた自然な音声対話
- 会話時のオーディオ出力に連動した口の動き（Phase 1で実装済みの仕組みを流用）
- 発話内容に応じた、目などによる感情表現
- 「30cm前進して」のような音声コマンドによる、Arduino制御の振る舞いのスムーズな呼び出し
- 弱いCPU上でも成立する、極力軽量なシステム

## 3. 各要素の仕様検討
 
### 3.1 音声認識（STT）
 
- Google Cloud Speech-to-Text等のクラウドSTTを想定。**クラウド利用のためネットワーク接続が必須**となり、Phase 1の非機能要件「オフライン環境での安定動作」とは相容れない。Phase 2はオンライン運用が前提になることを明記する。
- マイク入力デバイスが現状のハードウェア構成に存在しない（オミットしたWebカメラにマイクが内蔵されているが、今回は未使用）。Phase 2着手時にマイクをどう確保するか（USBハブのポート不足問題の再検討、カメラのマイクのみ活用、等）は未確定事項とする。
- アーキテクチャ上は `SpeechRecognizer` インターフェースとして抽象化し、Google STTをその一実装として実装する。
### 3.2 対話エンジン（Gemini API）
 
- テクロボくんの設定（性格：冷静で建設的、情報探索とお喋りが趣味、自分の好みや意見を強く持つ）をシステムプロンプトとして与え、ペルソナに沿った自然な応答を行わせる。
- `DialogueEngine` インターフェースとして抽象化：発話テキストを入力し、応答テキストを出力する。会話履歴の保持、将来のモデル切り替えはこの層に閉じ込める。
- API応答には通信のレイテンシが発生するため、Phase 1で汎用状態として設計しておいた`FacialEngine`の`LOADING`表示（読み込み中の目のクルクル回転アニメーション）を、そのままネットワーク応答待ちの視覚化に転用できる見込みである。Phase 1時点での設計意図（本来はLLM統合時の流用を見据えたもの）が、Phase 2で実際に活きる形となる。
### 3.3 TTS（音声合成）
 
| 項目 | Phase 1 | Phase 2 |
|---|---|---|
| 方式 | 事前収録（koeiroink）、最大10スロットに固定登録 | リアルタイム音声合成（候補：VOICEVOX、未定） |
| 入力 | スロット番号 | 任意のテキスト（Gemini API応答） |
 
- `TTSEngine` インターフェースとして抽象化し、Phase 1の実装（`AudioSlotRegistry`＋固定音声ファイル）を`PreRecordedTTSEngine`、Phase 2の実装を`RealtimeTTSEngine`として位置付ける。
- 音声出力後の振幅解析による口パク連動（`AudioPlayer`）は、音声ソースが「事前収録ファイルの再生」であっても「リアルタイム合成音声のストリーミング再生」であっても、Web Audio APIの解析ノードを再生経路に挟む形にしておけば共通のロジックで対応できる見込みである。Phase 1で`AudioPlayer`と`AudioSlotRegistry`を分離しておいた設計判断は、この置き換えを容易にする。
- VOICEVOX等のローカル音声合成エンジンは比較的重い処理であり、非力なCPU（Core m7-7Y25）上で実用的な速度で動作するかは未検証。Phase 2着手時の技術的懸念事項とする。
### 3.4 発話内容に応じた感情表現
 
- Gemini API側に、応答テキストとあわせて簡易的な感情ラベル（例：通常・疑問・喜び等）を出力させる方式が考えられるが、具体的な分類方式・粒度は未定。
- `EmotionEngine`という概念を導入し、発話内容（テキストまたは構造化データ）を表情パラメータへ変換する。Phase 1で`FacialEngine`の表示状態を`IDLE`/`SPEAKING`/`LOADING`として拡張可能な形に設計しているため、感情パラメータの追加はこの延長として自然に組み込める見込みである。
### 3.5 音声コマンドによる距離指定移動
 
「30cm前進して」等の自然言語コマンドを解析し、Arduino側の走行制御に変換する機能。
 
**技術的な懸念点**：現状のハードウェアには車輪エンコーダー等の移動量フィードバック手段が存在せず、走行制御は完全なオープンループである。そのため「正確に30cm」という精密な移動は原理的に困難であり、以下のいずれかの対応が必要になる。
 
1. 速度と時間から移動量を推定する、時間ベースのオープンループ制御（キャリブレーションを行うが、路面状況やバッテリー電圧変動等により誤差が生じる）
2. 将来的な車輪エンコーダー等のハードウェア追加の検討
3. 「だいたい30cm」程度の近似精度で割り切る運用
Phase 2の暫定方針としては1.（時間ベースのオープンループ制御）を採用し、精度要件が厳しくなった場合にハードウェア追加を検討することとする。
 
アーキテクチャ上は、自然言語コマンドを解析する `VoiceCommandParser` を新設し、方向と距離（または時間）を持つコマンドオブジェクトに変換する。Phase 1の`DriveStateMachine`は「w/s/a/d/rによる継続的なモード切り替え」という概念のみを持ち、「指定量だけ動いて自動的に停止する」という概念を持たないため、これを扱う新しい抽象（例：`TimedDriveCommand`）を別途追加する形になる見込みである。Phase 1の状態遷移表自体（4節）を変更する必要はないと考えられる。
 
### 3.6 カメラ
 
- 筐体には固定用の穴のみ存在し、ハードウェアは未接続（USBハブのポート不足のため大会機ではオミット）。
- 大会後、80mmファンの電源をUSBからレギュレーター直結に変更し、空いたUSBポートにカメラを接続する計画。
- 用途（会話相手の検知、表情認識、その他画像認識等）は未確定。本書では `CameraInput` インターフェースとしての抽象化のみ言及し、具体的な要件は接続後に別途検討する。
### 3.7 アイドル動作の精緻化
 
- Phase 1では「疑似乱数とインクリメントによって動作間隔にムラを持たせる」ことのみを確定仕様としている。
- Phase 2では、例えば会話相手の方向を意識した視線移動など、より生物的な挙動を検討する余地があるが、具体的な仕様はカメラ導入後、実機での検証を経て決定する。

## 4. Phase 1アーキテクチャのPhase 2拡張への耐性評価
 
Phase 1スペック9節で採用したモジュール構成（`InputSource` / `InputRouter` / `DriveStateMachine` / `AudioSlotRegistry` / `AudioPlayer` / `FacialEngine` / `DebugHUD` / `AppOrchestrator`）を前提に、Phase 2機能をどこまで無理なく受け入れられるかを評価する。
 
**そのまま流用・拡張できる見込みの箇所**
 
- `FacialEngine`の`LOADING`状態：ネットワーク応答待ち表示への転用が可能（3.2節）
- `AudioPlayer`の振幅解析ロジック：音声ソースがファイル再生かストリーミング再生かによらず共通化できる見込み（3.3節）
- `TTSEngine`インターフェースとして抽象化しておけば、`AudioSlotRegistry`（Phase 1）と`RealtimeTTSEngine`（Phase 2）を差し替え可能にでき、`AppOrchestrator`側の変更は最小限で済む見込み
**新規に追加が必要な抽象**
 
- `SpeechRecognizer`（STT）
- `DialogueEngine`（Gemini API対話）
- `VoiceCommandParser`（距離指定移動コマンドの解析）
- `EmotionEngine`（感情表現マッピング）
- `CameraInput`
これらはPhase 1のコードベースには存在しない新規インターフェースである。Phase 1の実装時点でこれらのダミー実装や骨組みまで先回りして用意する必要はない（過剰設計を避ける）が、Phase 1の各モジュールが疎結合に保たれている限り、Phase 2でこれらを追加してもPhase 1側の既存コードへの影響は限定的であると見込まれる。
 
- `DriveStateMachine`は「継続モード」概念専用のクラスとして閉じており、距離指定移動（「時限コマンド」概念）は別クラス（`TimedDriveCommand`等）として追加する形になる見込みで、Phase 1の状態遷移表自体（4節）の変更は不要と考えられる。

## 6. Phase 1スペックとの対応関係
 
| Phase 2の機能 | Phase 1での関連実装 | 関係性 |
|---|---|---|
| Gemini API対話の応答待ち表示 | `FacialEngine`の`LOADING`状態（音声スロット切り替え用） | そのまま転用見込み |
| リアルタイムTTSの口パク連動 | `AudioPlayer`の振幅解析ロジック | 共通化見込み |
| リアルタイムTTS本体 | `AudioSlotRegistry`（事前収録） | `TTSEngine`インターフェースで共存・差し替え |
| 距離指定移動 | `DriveStateMachine`（継続モード切り替え） | 別クラスとして新設、既存部分は変更不要見込み |
| 音声コマンド全般 | `InputRouter`（バーコードリーダー由来のキー入力振り分け） | 新たな入力系統（音声）として`InputRouter`に追加する形が自然 |
| 発話内容連動の感情表現 | `FacialEngine`の状態拡張余地 | 状態の追加として自然に拡張可能見込み |
