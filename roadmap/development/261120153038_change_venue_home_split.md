# 仕様変更：会場と自宅に分ける（claude.aiの改訂版 v6を取り込む）

- 状態: 承認済み（新版 261120154509、プランアセット v6）
- 対象: プランアセット v5 → v6、imple・tasks・walk（261114070529）→ 新版
- きっかけ: claude.aiの改訂版プランアセット（ルートの`tekurobokun_SPEC.md`ほか7ファイル）。前回の展示（261114）の振り返りを受けたもの

## 変更内容

スペックシートの冒頭の「変更点の要約」のとおり。要点だけを再掲する。

1. **バックエンドPCを自宅に置き、会場とはCloudflareの名前付きトンネル（仮に`tekurobo.nid-techtech.com`）でつなぐ**。会場は機体とconsoleだけ。インターネット接続が前提になる
2. **入力を機体のマイクに移す**。機体が無音検出（Silero VAD）で1発話ずつ区切ってWAVで送り、バックエンドがGoogle STT（V2 `Recognize`）で文字にする。再生中はマイクを止める（半二重）
3. **返事を`{say, emotion, search}`にし、必要なときだけTavilyで1回検索して答え直す**
4. **モデルを正Qwen3-8B・副Qwen3-4Bに変える**（GPUはRX 5700 XT 8GB）。比較スクリプトでQwen3.5-9B・4Bと比べる
5. **新しいアプリ`apps/launcher`（Tauri）**：5つのサービスの起動・監視・正→副の切り替え、入力元の切り替え、マイクの一時停止、会話のリセット、登録コード（QR）、端末の一覧。サインイン時に自動起動。会場からはChrome Remote Desktopで操作する
6. **端末の登録とトークン**：機体はQRをカメラで、consoleは文字で登録コードを入れて、長期のトークンと交換する。管理用APIは`127.0.0.1:8788`だけで待ち受ける
7. **consoleは普段ログの表示専用**（S01h）。入力元をconsoleに切り替えたときだけv5の入力ページ（S01a〜S01g）
8. **一定時間（90秒）だれも話さなければ、LLMに渡す履歴を消す**。自己認識を人格プロンプトの先頭で固定し、質問が続いたら意見を言わせる
9. **走行を使う**：機体のキーボードのWASDで、押している間だけ動く。Arduinoの受信タイムアウト（200ms）との二重の停止
10. **タスクスケジューラでの自動起動（v5のT5-2・T5-3）をランチャーに置き換える**。`scripts/register_backend_tasks.ps1`・`unregister_backend_tasks.ps1`は廃止
11. **モックを画面ごとのファイル（S01・S02・S03）に分け**、v5の「モックとの差分」を取り込んだ。マスターSVGにレイヤーの`id`を付けた（形は同じ）。トークンとbrandは変更なし
12. バージョンは`0.2.0`

## 理由と影響

- 振り返りの課題（作り話、自己認識のぶれ、質問のループ、3秒の待ち、会場に持ち込む機材の多さ、履帯への関心）に応えるため
- W3-8で未決だった「機体の発話をタブレットのディクテーションが拾う」問題は、入力が機体のマイク（半二重）に移るため、この版で解消する
- 外部サービス（Google STT・Tavily・Cloudflare）に依存するようになる。開発機ではすべてスタブに替えて動かす（v5の3段階の検証は「スタブ → 開発機で実際のAPI → 自宅のバックエンドPCと会場」になる）
- 来場者の声と検索語が外部に送られるため、READMEの注意事項（v5は「外部に送らない」）と掲示の文言を書き直す
- 規模が大きいため、Phaseを7つ（Phase 6〜12）足す

## 解析で気づいた点（新版のimpleでこう扱う）

承認の判断に関わるもの。異論があれば承認時に指示してほしい。

1. **公開用ポートの待ち受け先**：cloudflaredは`localhost:8787`へつなぐため、本番の公開用ポートは`127.0.0.1`で待ち受けられる。こうすると、Cloudflareのヘッダー（`CF-Connecting-IP`）を偽って直接つなぐ経路がなくなり、v5のファイアウォールの8787の許可も不要になる。待ち受け先を設定にし、本番は`127.0.0.1`、開発機でLANから試すときだけ`0.0.0.0`にする
2. **backend → ランチャーの知らせ**（LLMが時間内に返事をしなかった）：管理用APIはランチャーが呼ぶ向きのため、管理用APIに状態とできごとを流すWebSocket（`/admin/events`）を置き、ランチャーはそれを購読する
3. **正副の切り替えをbackendが知る方法**：ポートは同じなので、ランチャーが切り替えたあと、管理用APIでbackendに「いまのモデルの別名」を伝える。backendは別名ごとの設定（`DialogueEngine`）とログの`model`に使う
4. **STTの費用を抑える**：機体は、会話が待機中で、かつ自分が入力元のときだけ音声を送る。backendも待機中以外・入力元以外の音声はSTTに渡さずに捨てる
5. **ランチャーができる前の登録**：Phase 6では、開発用のCLI（`bun run admin pair`など。登録コードを文字で出し、QRをSVGに書き出す）で管理用APIを呼んで試す。ランチャーのQRの生成にも、読み取りと同じ`zxing-wasm`（writer）を第一候補にする（着手時に確かめる）
6. **Arduinoのスケッチ**：ヘボコン版（`../tekurobokun-lite/arduino_sketch/`）に`COMMAND_TIMEOUT_MS = 200`の受信タイムアウトがあることを確かめた。スケッチは中身を変えずに`apps/robot/arduino/`へコピーし、このリポジトリで管理する
7. **Tauri 2.12の`on_permission_request`、ランチャーのautostartプラグイン、Google STTの認証（サービスアカウントの鍵からのトークン）、Tavilyの無料枠を超えたときの扱い**は、着手時に公式ドキュメントとインストール済みの版で確かめる（スペックシートのとおり）

## 実機を要する検証の配置（ユーザーの指示による例外）

ユーザーの手元に開発機（Windows）しかなく、実機で検証できないため、重要な部分の実装を先に進める（261120の指示）。`agentic-roadmap`の「後回しを前提にした配置はしない」の例外として、次のように組む。

- **実機**とは、機体（Core m7）、Arduinoと履帯、タブレット・スマホ、バックエンドPC（RX 5700 XT）、名前付きトンネルと会場の回線を指す。開発機のマイク・スピーカー・カメラ、開発機から呼ぶGoogle STT・Tavily、開発機のCPUで動かすllama-server（Qwen3-4B）とVOICEVOXは、実機に含めない
- Phase 6〜10のwalkには、開発機で確かめられる項目だけを置く（スタブ、単体テスト、開発機のマイクとスピーカーでの半二重、開発機のカメラでのQR読み取り（カメラがなければ、生成したQRの画像を読む単体テスト）、実際のAPI）。各Phaseはこれが通れば次へ進む
- 実機でしか確かめられない検証は、Phase 11「実機での検証と本番の準備」にまとめる。Phase 5のW5-3（字幕の実機確認）とW5-5（アイコンとファビコン）も、Phase 11へ移す
- **走行は、Phase 11で実機の停止の検証（キーを離す・フォーカスを失う・ケーブルを抜く・アプリを止める）が通るまで、会場で使わない**。それまでは設定の「走行を使う」を既定で無効にしておく
- Phase 11で見つかった問題は、規模に応じて軽微な修正（fix）か仕様変更として扱い、Phase 11の中で直して再検証する。実装を先に進めた分、Phase 7〜9のコードの手直しになることがある（Core m7でのVADの負荷、実機のスピーカーとマイクの回り込み、機体のWebView2の許可、Arduinoとのシリアル通信など）
