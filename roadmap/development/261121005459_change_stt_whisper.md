# 仕様変更：音声認識をローカルのwhisper.cppにし、実機の検証を各Phaseへ移す（claude.aiの改訂版 v7を取り込む）

- 状態: 承認済み（新版 261121012004、プランアセット v7）
- 対象: プランアセット v6 → v7、imple・tasks・walk（261120154509）→ 新版
- きっかけ: claude.aiの改訂版プランアセット（ルートの`tekurobokun_SPEC.md`ほか7ファイル）と、ユーザーが自宅に戻り、バックエンドPCと機体の実機で検証できるようになったこと（261121の指示）

## 変更内容

### A. 音声認識をwhisper.cppにする（スペックシートの「変更点の要約」のとおり）

1. **音声認識を、Google Cloud Speech-to-Text V2から、バックエンドPCの`whisper-server`（whisper.cpp 1.9系、Vulkan、`ggml-large-v3-turbo-q5_0.bin`）に替える**。日本語に固定し、翻訳しない。ポートは8081。来場者の声は外部に送らない
2. **決まり文句（「ご視聴ありがとうございました」など。一覧は設定）だけの結果と、`whisper-server`が音声なしと判断した結果を、空の発話として捨てる**
3. **ランチャーのサービスを6つにする**（`stt`を足す）。［すべて起動］は`llm.main`の読み込みが終わってから`stt`を起動する（VOICEVOXはLLMを待たない）。正→副の切り替えでは`stt`を止めない。外部サービスの行はTavilyの検索回数だけ
4. **音声認識の比較スクリプトを足す**：録音のセット（16kHzモノラルのWAVと正解の文、無音・雑音だけの録音を含む）を、モデルごと（large-v3-turbo q5_0・q8_0、kotoba-whisperなど）に流し、認識結果・文字の誤り率・時間・捨てた数を一覧にする
5. **Google STTの実装を消す**：`GoogleSpeechRecognizer`（`apps/backend/src/stt/google.ts`）、`google_auth.ts`、`scripts/stt_locations.ts`とそのテスト、`package.json`の`stt:locations`、設定の`stt.google`。`SpeechRecognizer`の抽象とスタブ、`health.stt`は残す
6. **GPUのメモリ**：RX 5700 XT（8GB）にllama-server（Qwen3-8B）と`whisper-server`を同時に載せる（見積もり約7.3GB）。実機で会話中の最大値を測り、足りなければ文脈の長さかKVキャッシュの量子化で収める
7. プライバシー・費用・秘密の値の記述からGoogle STTを外す。モックの変更はS03（サービスの行、外部サービス、決まったこと）と、S01f・S02eの見出しの文言だけ。トークン・brand・マスターSVGは変更なし

### B. 実機の検証を各Phaseのwalkへ移す（ユーザーの指示）

v6では、ユーザーの手元に開発機しかなかったため、実機の検証をPhase 11にまとめた（`261120153038_change_venue_home_split.md`の「実機を要する検証の配置」。`agentic-roadmap`の「後回しを前提にした配置はしない」の例外）。自宅でバックエンドPCと機体を使えるようになったため、この例外をやめ、各検証を、依存する実装がそろう最初のPhaseに戻す。

- Phase 7：バックエンドPCの準備（GPU、llama-server、whisper-server）、機体の実機の準備と登録、録音のセットと音声認識のモデルの決定、GPUのメモリの測定、機体の実機のマイクとスピーカーでの会話、字幕
- Phase 8：正のモデルと文脈の長さの決定（バックエンドPCのGPU）、正のモデルでの自己認識と質問のループ、機体の実機での調べ中の顔、タブレット・スマホでのconsoleの表示
- Phase 9：Arduinoと履帯をつなぎ、実機で走行と停止を確かめる（通るまで`drive.enabled`は`false`のまま）
- Phase 10：名前付きトンネル、バックエンドPCの本番の準備（ランチャーのインストールと自動起動）、GPUでの正→副の切り替え、再起動からの無人の立ち上げ、ランチャーのQRでの登録、アイコン
- Phase 11：「会場と同じ条件での通し」だけにする（モバイルルーター、スマホからのChrome Remote Desktop、応答時間の測定）

## 理由と影響

- 来場者の声を外部に送らずに済み、STTの費用と鍵の管理（Google Cloudの準備、T7-6）がなくなる。その代わり、バックエンドPCで`whisper-server`をビルドし、GPUのメモリをLLMと分け合う
- 実機の検証を最後にまとめると、Phase 7〜9のコードの手直しが積み重なる（v6のchangeで予告していたもの：Core m7でのVADの負荷、スピーカーとマイクの回り込み、WebView2の許可、シリアル通信）。実機があるいま、各Phaseで確かめるほうが手戻りが小さい
- 完了済みのPhase 7の項目のうち、T7-2（`GoogleSpeechRecognizer`を含む）は完了のまま残し、Google STTの部分は新しい項目で消す

## 解析で気づいた点（新版のimpleでこう扱う）

承認の判断に関わるもの。異論があれば承認時に指示してほしい。

1. **バックエンドPCでもClaude Codeを使う**（261121のユーザーの回答）：ソフトの準備（`whisper-server`のビルド、llama-serverとモデルの取得）、比較スクリプトの実行、GPUのメモリの測定、ランチャーの切り替えの確認は、バックエンドPCのClaude Codeで行う【エージェント】の項目にする。項目の本文の頭に「（バックエンドPCで）」と書く。ハードウェア・ドライバー・SDKのインストーラー・アカウントの操作（Cloudflare、Chrome Remote Desktop、自動サインイン）と、モデルの決定（スペックシートの未決事項）は【ユーザー】のまま
   - **機械の切り替え**：開発機とバックエンドPCの間は、Gitで受け渡す。バックエンドPCの項目の前で、エージェントは引き継ぎメモとコミットメッセージを書いて停止し、ユーザーがコミット・push、バックエンドPCでpullしてから再開する（逆も同じ）。`config/*.local.json`と`data/`はGit管理外のため、機械ごとに置く
   - `scripts/setup_whisper.ps1`（版を固定し、置き場所はリポジトリの外、llama.cppとは別のフォルダ）は、開発機ではCPU版か小さいモデルで、バックエンドPCではVulkan版で動かせるようにする
2. **Phase 7〜9の実機の接続は自宅のLAN**：名前付きトンネルの作成はランチャーの`tunnel`サービスと合わせてPhase 10に置く。それまでは、バックエンドの公開用ポートを`0.0.0.0`で待ち受け、`publicUrl`をLANのアドレスにして、機体とタブレット・スマホを登録する（v6のT6-9で書いた「LANから試すとき」の手順）。各サービスはPhase 10まで手で起動する
3. **実機の範囲**：バックエンドPC（RX 5700 XT）、機体（Core m7、カメラ・マイク・スピーカー、Arduinoと履帯）、タブレット・スマホは自宅にある前提とする。モバイルルーターがなければ、Phase 11はスマホのテザリングなどで代える
4. **`health.stt`の確かめ方**：`whisper-server`に専用の受け口があるか、軽い問い合わせで代えるかは、インストールした版のソースで確かめる（スペックシートのとおり着手時）。ランチャーが`stt`をLLMの後に起動するため、起動直後の数十秒は`health.stt`が`false`になり、機体はS02e（眠っている）になる。v6の「応答しないときはS02e」と同じ扱いでよいとする
5. **決まり文句の一覧と音声なしのしきい値**：既定の一覧を`config/backend.default.json`に置き、`config/backend.local.json`で上書きできるようにする。照らし方は、前後の空白と句読点を除いた全体の一致を基本とする（部分一致にすると本当の発話を捨てやすいため）。最終の値は録音のセットで決める
6. **比較スクリプト**：対話の比較（`scripts/bench_dialogue.ts`）とは別のスクリプト`scripts/bench_stt.ts`にする。モデルごとに`whisper-server`を起動し直して流す。録音のセットは`data/stt_bench/`（Git管理外）に置く。録音には来場者の声を使わず、ユーザー自身の声で作る
7. **録音のセットは機体のマイクで作る**：会場と同じマイクの特性で比べるため。録音の道具は問わない（16kHzモノラルのWAVで書き出せればよい）
8. **GPUのメモリの測定の順**：Phase 7で、Qwen3-8B（文脈4K）と`whisper-server`を同時に載せて測る。足りない場合の対処（文脈の長さ、`-ctk q8_0 -ctv q8_0`）はPhase 7で決めて設定に書き、Phase 8の正のモデルの決定はその範囲で行う
